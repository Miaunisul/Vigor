# Migrations do Banco de Dados — VIGOR

## 1. Objetivo

Este documento descreve como o VIGOR versiona o schema PostgreSQL com Flyway, registra as migrations existentes e orienta a execução e a consulta do histórico. As migrations preservam um histórico ordenado das alterações do schema e mantêm sua evolução alinhada ao mapeamento JPA.

## 2. Configuração atual

O projeto declara no `pom.xml` o `spring-boot-starter-flyway`, o módulo `flyway-database-postgresql` e o driver JDBC do PostgreSQL. Os scripts versionados estão no local padrão `src/main/resources/db/migration/` e são descobertos pelo Flyway durante a inicialização da aplicação.

O arquivo `application.properties` configura a conexão local para `jdbc:postgresql://localhost:5432/vigor`, com o usuário `postgres` e a senha fornecida por `DB_PASSWORD`. Não há senha literal documentada ou versionada neste projeto.

O Hibernate está configurado com `spring.jpa.hibernate.ddl-auto=validate`. Nessa configuração, o Hibernate compara o mapeamento das entidades com o schema existente e falha na inicialização quando encontra divergências relevantes. Ele não cria nem altera tabelas. O Flyway é responsável por aplicar e registrar as alterações do schema; o Hibernate valida o resultado em relação às entidades JPA.

## 3. Migrations existentes

Todas as tabelas usam `id BIGINT GENERATED BY DEFAULT AS IDENTITY` como chave primária e colunas obrigatórias declaradas como `NOT NULL` nas migrations.

### V1 — `V1__cria_tabela_membros.sql`

Cria `membros` com `nome VARCHAR(150)`, `cpf VARCHAR(11)`, `telefone VARCHAR(20)`, `endereco VARCHAR(255)` e `data_cadastro DATE`. Todas as colunas, exceto o identificador que é chave primária, são obrigatórias. A constraint `uk_membros_cpf` torna o CPF único. Esta migration não define chave estrangeira nem índices adicionais.

### V2 — `V2__cria_funcionarios.sql`

Cria `funcionarios` com `nome VARCHAR(150)`, `cargo TEXT`, `login TEXT` e `senha_hash TEXT`, todos obrigatórios. Os checks `ck_funcionarios_nome_nao_vazio`, `ck_funcionarios_cargo_nao_vazio`, `ck_funcionarios_login_nao_vazio` e `ck_funcionarios_senha_hash_nao_vazio` rejeitam valores vazios após `btrim`. O índice único funcional `ux_funcionarios_login_normalizado` em `lower(btrim(login))` impede logins duplicados que diferem por maiúsculas/minúsculas ou espaços comuns nas extremidades. Não há chave estrangeira nesta tabela. A migration não insere funcionários; `senha_hash` é uma coluna textual obrigatória e o script não verifica se seu conteúdo é um hash BCrypt.

### V3 — `V3__cria_treinos.sql`

Cria `treinos` com `membro_id BIGINT`, `tipo TEXT`, `descricao TEXT`, `duracao_minutos INTEGER` e `data_inicio DATE`, todos obrigatórios. Os checks `ck_treinos_tipo_nao_vazio` e `ck_treinos_descricao_nao_vazia` rejeitam texto vazio; `ck_treinos_duracao_positiva` exige duração maior que zero. A FK `fk_treinos_membros` referencia `membros(id)` com `ON DELETE RESTRICT`. O índice `idx_treinos_membro_id` atende consultas por membro.

### V4 — `V4__cria_pagamentos.sql`

Cria `pagamentos` com `membro_id BIGINT`, `valor NUMERIC(12,2)`, `data_pagamento DATE` e `status VARCHAR(4)`, todos obrigatórios. `ck_pagamentos_valor_positivo` exige valor maior que zero e `ck_pagamentos_status_pago` permite exclusivamente `PAGO`. A FK `fk_pagamentos_membros` referencia `membros(id)` com `ON DELETE RESTRICT`. O índice `idx_pagamentos_membro_id` atende consultas por membro.

### V5 — `V5__cria_historico_atividades.sql`

Cria `historico_atividades` com `membro_id BIGINT`, `funcionario_responsavel_id BIGINT`, `atividade TEXT`, `data_atividade DATE` e `tempo_execucao_minutos INTEGER`, todos obrigatórios. `ck_historico_atividades_atividade_nao_vazia` rejeita atividade vazia após `btrim`; `ck_historico_atividades_tempo_positivo` exige tempo maior que zero. As FKs `fk_historico_atividades_membros` e `fk_historico_atividades_funcionarios` referenciam, respectivamente, `membros(id)` e `funcionarios(id)`, ambas com `ON DELETE RESTRICT`. O índice `idx_historico_atividades_membro_id` atende consultas por membro. A migration não cria índice adicional por funcionário.

As FKs das V3, V4 e V5 impedem referências a registros inexistentes. `ON DELETE RESTRICT` impede excluir membros com treinos, pagamentos ou atividades vinculados, e impede excluir funcionários responsáveis por atividades relacionadas. Não há exclusão em cascata nas migrations.

## 4. Versionamento e integridade

Os arquivos seguem o padrão `V<versão>__<descricao_curta>.sql`: prefixo `V`, versão numérica, dois sublinhados e descrição em letras minúsculas separadas por sublinhados. O Flyway aplica migrations pendentes na ordem crescente e registra cada resultado em `flyway_schema_history`.

Uma migration versionada que já foi aplicada não deve ser editada para mudar seu efeito. Alterações posteriores devem ser registradas em uma nova versão. Antes de introduzir novas constraints ou mudanças de estrutura, deve-se avaliar compatibilidade e dados existentes; não se deve apagar ou transformar dados sem decisão e procedimento documentados.

## 5. Configurar e executar localmente

Antes de iniciar, disponibilize o PostgreSQL local, o banco `vigor` e a variável `DB_PASSWORD` no mesmo processo que executará a aplicação. Não inclua a senha em arquivos do projeto ou neste documento.

**Windows PowerShell:**

```powershell
$securePassword = Read-Host -Prompt "Senha do PostgreSQL" -AsSecureString
$credential = [System.Management.Automation.PSCredential]::new("postgres", $securePassword)
$env:DB_PASSWORD = $credential.GetNetworkCredential().Password
try {
    .\mvnw.cmd spring-boot:run
}
finally {
    Remove-Item Env:DB_PASSWORD -ErrorAction SilentlyContinue
    Remove-Variable securePassword, credential -ErrorAction SilentlyContinue
}
```

**Linux ou macOS (Bash):**

```bash
export DB_PASSWORD="<senha-local>"
./mvnw spring-boot:run
```

O Flyway aplica as migrations pendentes durante a inicialização. Para consultar o histórico, conecte um cliente SQL ao banco `vigor` e execute:

```sql
SELECT installed_rank, version, description, type, script, success
FROM flyway_schema_history
ORDER BY installed_rank;
```

Em um banco preexistente, o histórico pode conter uma linha `BASELINE`; nesse caso, ela registra a adoção do schema e não significa que o script da versão indicada foi executado nesse banco. A estratégia de adoção deve ser conferida para cada banco antes da inicialização.

## 6. Resultado da validação em banco vazio

Na validação informada para um banco PostgreSQL vazio, o Flyway executou com sucesso as cinco migrations, da V1 à V5. Após a aplicação delas, a aplicação iniciou sem divergências de schema detectadas pelo Hibernate/JPA com `ddl-auto=validate`.

Esse resultado comprova a aplicação das migrations e a validação do mapeamento nessa execução. Ele não representa, por si só, a execução de todos os testes funcionais ou de persistência dos módulos.

## 7. Fluxo para futuras alterações

1. Conferir a necessidade em relação aos requisitos, regras de negócio e [modelo de dados](modelo-de-dados.md).
2. Registrar impactos sobre schema, integridade, compatibilidade e dados existentes.
3. Criar uma nova migration com versão crescente, sem reescrever versões aplicadas.
4. Revisar a migration junto com as alterações Java e os testes pertinentes.
5. Aplicar e verificar a sequência em cada ambiente e consultar `flyway_schema_history`.
6. Planejar backup e recuperação conforme o ambiente antes de alterações que possam afetar dados.

## 8. Pendências operacionais

- Definir e documentar o procedimento de backup e recuperação para cada ambiente.
- Para outros bancos preexistentes, comparar o schema real e decidir como incorporá-los ao histórico Flyway antes de iniciar a aplicação.
- Executar os testes de persistência e integração PostgreSQL com as credenciais de teste disponíveis; a validação de schema não substitui esses testes.
- Definir o procedimento de aplicação e revisão das migrations nos ambientes além do local e da validação em banco vazio descrita acima.
